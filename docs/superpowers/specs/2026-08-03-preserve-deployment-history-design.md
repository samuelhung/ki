# 保留部署历史设计

## 背景

即时快报退役发布必须保留现有版本目录和部署数据库备份。当前后端部署器在发布成功后调用 `prune_versions` 和 `prune_daily_backups`，会删除部分历史，和本次生产约束冲突。

## 方案

为 `deploy_backend.py` 增加显式命令行参数 `--preserve-history`，并将其保存到 `BackendDeployConfig`。

- 默认不启用，保持既有发布清理策略不变。
- 启用时，发布成功后跳过 `prune_versions` 和 `prune_daily_backups`。
- 不改变发布前数据库备份、版本安装、`current` 原子切换、健康检查或失败自动回滚。
- 本次 `2.0.0+106` 生产发布必须显式传入该参数。

不采用永久删除清理逻辑的方案，因为其他部署仍可能需要现有保留策略；不采用发布前手工复制历史的方案，因为会制造重复数据，也不能阻止部署器随后删除原历史。

## 验证

自动化测试覆盖以下行为：

1. 默认配置继续调用版本和备份清理。
2. `--preserve-history` 启用时，两类清理都不调用。
3. 参数能从 CLI 正确传入部署配置。
4. 原有成功发布、失败回滚和 `launchd` 竞态测试继续通过。

生产验收在发布前后分别记录 `runtime/versions` 和 `backups/deploy-*.sqlite` 的文件名集合，并断言发布后没有历史项减少；同时完成健康、数据库一致性、旧快报 API、现有 API 方法语义和前端 UI 验收。

## 边界

该参数只影响成功发布后的历史清理。它不会恢复已删除的即时快报数据，不会创建额外历史副本，也不会删除失败的 `2.0.0+105` 目录或任何旧备份。
