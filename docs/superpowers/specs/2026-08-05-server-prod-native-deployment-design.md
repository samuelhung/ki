# server-prod 原生部署与迁移设计

## 目标

将知己正式环境从 Intel Mac `zhiji-prod` 迁移到 Ubuntu 主机
`server-prod`（`root@10.8.0.45`），并建立不依赖 Codex 的终端一键部署流程。

日常发布由操作者在本地项目目录运行：

```bash
./scripts/deploy-production
```

正常发布目标为 3–5 分钟。部署必须来自已推送的 `origin/main`，使用版本化
wheel、SHA-256 制品校验、原子版本切换、systemd 托管、部署前数据库备份和
失败自动回滚。

## 已确认约束

- 不使用 Docker。
- 正式地址改为 `http://10.8.0.45:9120`。
- 局域网设备可通过 `http://192.168.100.163:9120` 访问。
- 只允许 `10.8.0.0/24` 和 `192.168.100.0/24` 访问端口 `9120`。
- 新环境从空数据库开始，不迁移旧内容、媒体、日志、版本或部署备份。
- 迁移现有 AI、火山引擎和 TOS 配置，但重新生成 `KI_API_TOKEN`。
- 旧 `zhiji-prod` 不作为迁移后的回滚环境保留。
- 密钥不得进入 Git、命令参数、命令输出或部署日志。
- 首次初始化可由 root 完成；日常部署和服务运行不得使用 root。
- 保留现有 `--preserve-history` 能力，不通过提速取消备份、校验或回滚。

## 主机基线

现场只读审计确认 `server-prod` 为 Ubuntu 20.04、x86_64、16 逻辑 CPU、
31 GiB 内存。系统 NVMe 根盘剩余约 323 GiB，`/data` 挂载盘剩余约
12 TiB，时区为 `Asia/Shanghai`，`9120` 当前未被占用。

主机已有 systemd、UFW、Nginx、Docker 和大量其他业务。知己不依赖宿主机
Python 3.8、Node 20 或其他项目的全局运行时，也不修改已有 Nginx 站点和
Docker 工作负载。

## 文件布局

程序和工具链放在系统 NVMe 盘：

```text
/srv/apps/zhiji/
  packages/<git-sha>/                 上传并校验后的发布制品
  versions/<release-tag>/             每个版本独立的 Python 虚拟环境
  current -> versions/<release-tag>   当前运行版本的原子软链接
  toolchains/                         固定 Python 3.12 和 FFmpeg
  cache/                              按锁文件哈希复用的依赖缓存
```

持续增长的业务数据和短期备份放在 `/data` 挂载盘：

```text
/data/apps/zhiji/                      SQLite、采集文件、状态和日志
/data/backups/zhiji/                   部署前数据库备份
```

服务配置放在：

```text
/etc/zhiji/zhiji.env
```

配置文件由专用 `zhiji` 用户持有，权限为 `0600`。程序、数据和服务均以该
非 root 用户运行。首次初始化后，本地 SSH 配置提供不使用 root 的稳定部署入口。

## 运行时与服务

首次初始化安装项目专用、固定版本的 CPython 3.12 和 FFmpeg，不替换宿主机
全局 Python 或 FFmpeg。每个应用版本创建独立虚拟环境；Python 依赖锁未变化
时复用服务器缓存，变化时才刷新缓存。

`zhiji.service` 由 systemd 托管，其启动目标固定为：

```text
/srv/apps/zhiji/current/venv/bin/python -m zhiji_backend.cli
```

服务读取 `/etc/zhiji/zhiji.env`，数据根目录指向 `/data/apps/zhiji`，工具链
路径由 systemd 显式设置。服务配置启用自动重启、启动超时、文件权限限制和
日志归档。健康检查始终从服务器本机访问 `http://127.0.0.1:9120`，不依赖
UFW 或覆盖网络状态。

## 命令边界

### 一次性初始化

```bash
./scripts/provision-production
```

该命令只用于新主机初始化，并要求明确确认目标主机身份。它负责：

1. 验证 `server-prod` 的 IP、系统、架构、时区、磁盘和端口。
2. 创建 `zhiji` 用户、目录、权限和非 root SSH 部署入口。
3. 安装并校验项目专用 Python 3.12 与 FFmpeg。
4. 安装、启用但暂不切换业务流量的 `zhiji.service`。
5. 写入仅允许两个已确认网段访问 `9120` 的 UFW 规则。
6. 检查 `/etc/zhiji/zhiji.env` 的所有权、权限和必需配置名称，但不打印值。

该命令必须可重复执行；已满足的步骤只验证，不重复破坏性修改。它不上传旧
数据库，也不停止旧正式服务。

### 日常部署

```bash
./scripts/deploy-production
```

该命令是唯一的日常正式发布入口，并依次执行：

1. 验证本地提交等于已推送的 `origin/main`，拒绝错误分支、未推送提交和会
   影响制品的未提交修改。
2. 固定 Node、Python、uv 和 npm 缓存路径，执行发布所需测试与前端构建。
3. 构建包含 Web UI 的后端 wheel，并生成包含 Git SHA 的发布元数据和
   SHA-256 校验清单。
4. 通过 SSH/SCP 上传到 `/srv/apps/zhiji/packages/<git-sha>`。上传在独立
   暂存目录中进行，未完成上传不能成为可部署制品。
5. 服务器复核 SHA-256、来源 SHA、版本号、锁文件哈希、配置权限、磁盘和
   当前服务状态。
6. 创建新的版本目录和独立虚拟环境，安装 wheel，并在切换前完成导入检查。
7. 停止服务，使用 SQLite backup API 创建一致性备份，原子切换 `current`，
   启动 systemd 服务。
8. 检查健康接口、数据库、PID、端口、systemd 状态和最新错误日志。
9. 输出一份短摘要，包括版本、Git SHA、目标主机、耗时和正式地址。

正常代码变更只上传约 1 MB。首次依赖准备或依赖锁变化时才会产生额外下载。

## 版本切换与失败处理

部署在停止服务前完成所有可提前完成的校验、上传、依赖安装和版本准备，以
缩短不可用时间。

任何以下情况均在切换前失败：目标主机不匹配、来源不是 `origin/main`、配置
不完整或权限不安全、端口冲突、磁盘不足、制品校验失败、版本目录已存在但
内容不匹配、Python/FFmpeg 版本错误或应用导入失败。

切换后的健康检查失败时，部署器必须：

1. 停止失败的新版本。
2. 恢复部署前数据库备份。
3. 将 `current` 切回上一版本。
4. 启动上一版本并执行降级健康检查。
5. 保留明确错误摘要；不得打印环境变量值。

`--preserve-history` 保留所有历史版本和部署数据库备份。历史清理不得作为
日常发布的隐式副作用；未来若需要清理，必须使用独立、可预览的维护命令。

## 网络与访问控制

服务监听 `0.0.0.0:9120`，UFW 只增加以下规则：

```text
ALLOW 9120 FROM 10.8.0.0/24
ALLOW 9120 FROM 192.168.100.0/24
DENY  9120 FROM OTHER SOURCES
```

`KI_ALLOWED_HOSTS` 包含 `10.8.0.45`、`192.168.100.163`、`127.0.0.1` 和
`localhost`。远程请求继续使用新的 `KI_API_TOKEN`。本次不引入公网访问、
TLS、域名或 Nginx 反向代理。

## 首次迁移流程

1. 完成部署工具实现和本地自动化验证。
2. 对 `server-prod` 执行只读预检。
3. 运行 `provision-production`，完成非 root 运行环境、工具链、systemd 和
   UFW 初始化。
4. 安全迁移 AI、火山引擎和 TOS 配置，重新生成 `KI_API_TOKEN`。迁移工具
   只校验配置名称和文件权限，不回显配置值。
5. 运行 `deploy-production`，从空数据目录部署当前 `origin/main`。
6. 验证健康接口、空数据库初始化、远程解锁、抖音采集、FFmpeg 转码、火山
   引擎转写、AI 标题和主要页面。
7. 新环境验收通过后，停止并禁用旧 Mac 的 `com.zhiji.backend`。
8. 旧程序和数据不作为回滚环境保留。实际删除旧数据属于独立破坏性操作，
   必须在新环境验收通过后再次确认，不能夹在自动部署命令中静默执行。

新环境可以先启动并验收，再停止旧环境，因此正式切换可以接近零停机。迁移
期间两套环境使用不同数据库，不存在双写或最终数据同步。

## 验证策略

### 自动化测试

- 编排器参数、主机身份、`origin/main` 和脏工作区门禁。
- SCP 暂存、SHA-256 校验和重复运行幂等性。
- systemd 单元生成、非 root 运行、环境文件权限和显式工具链路径。
- 空数据库初始化、SQLite 一致性备份和恢复。
- 成功部署、切换前失败、切换后失败、完整回滚和回滚失败报告。
- 双网段 UFW 规则生成以及其他来源不被允许。
- 摘要输出不包含 token、密钥、环境变量值或完整敏感 URL。

### 隔离集成测试

在临时根目录和非生产端口上运行 Linux 形态的版本安装、软链接切换、systemd
命令适配和健康检查。测试不得连接或修改两台正式主机的数据目录。

### 首次生产验收

- `systemctl is-active zhiji.service` 为 active，运行用户不是 root。
- `current` 指向预期版本，发布元数据中的 Git SHA 等于 `origin/main`。
- SQLite `quick_check` 和外键检查通过。
- `127.0.0.1:9120`、`10.8.0.45:9120` 和
  `192.168.100.163:9120` 在各自允许来源可访问。
- 非允许来源不能访问 `9120`。
- 提交一个真实抖音分享，处理队列完整更新并最终生成内容。
- 转写、标题修改、AI 生成标题和媒体播放通过真实浏览器验收。
- 观察 systemd 状态和错误日志至少 35 秒，并与页面验收并行执行。

## 时间与上传量

- 一次性实现和验证部署工具：预计 2–4 小时。
- 首次初始化和迁移：预计 30–45 分钟，网络异常时可能接近 60 分钟。
- 日常发布：预计 3–5 分钟。
- 当前应用 wheel 约 827 KB，日常制品总上传量约 1 MB。

## 不在本次范围

- Docker 或容器化部署。
- 迁移旧数据库、内容、媒体、日志、发布版本和备份。
- 保留旧 Mac 作为迁移后的回滚服务器。
- 自动删除旧 Mac 上的程序或数据。
- Ubuntu 大版本升级、Ubuntu Pro 接入或全主机安全整改。
- 调整服务器上其他 Nginx、Docker、MySQL、Redis、Java 或媒体业务。
- 公网开放、TLS、域名、反向代理或负载均衡。
- GitHub Actions 自动发布。
