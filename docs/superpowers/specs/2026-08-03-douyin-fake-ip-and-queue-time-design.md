# 抖音 Fake-IP 下载与队列北京时间修复设计

## 目标

修复两个已在线上复现的问题：抖音分享任务在下载阶段被 SSRF 防护误拦截，以及处理队列把数据库 UTC 时间直接显示为本地时间。

## 已确认根因

- 生产机把 `aweme.snssdk.com` 解析到代理软件的 RFC 2544 Fake-IP 地址 `198.18.0.190`。当前远程媒体传输层只接受 `ipaddress.is_global` 地址，因此在建立连接前抛出“远程视频地址必须解析到公网 IP”。
- `ingest_tasks.created_at` 使用 SQLite `CURRENT_TIMESTAMP` 正确保存 UTC。`GlobalDockQueueOverlay.tsx` 直接截取该字符串，没有调用项目已有的 `formatTimeBeijing`。

## 方案

### Fake-IP 兼容

保留通用远程传输层对私网、回环、链路本地和保留地址的拒绝规则。仅在抖音下载入口为受信任的 HTTPS CDN 主机启用受限兼容：允许 RFC 2544 的 `198.18.0.0/15` 作为代理 Fake-IP 连接目标。

允许条件必须同时满足：

1. URL 使用 HTTPS；
2. 主机为明确的抖音媒体域名（本次至少覆盖 `aweme.snssdk.com`，并沿用现有 `365yg.com` 媒体域名判断）；
3. 地址位于 `198.18.0.0/15`；
4. TLS 仍按原始主机名校验证书，Host 头仍使用原始主机名；
5. 每次重定向都重新执行同样的 URL、主机和地址验证。

不允许普通 HTTP 使用 Fake-IP，不允许任意域名使用 Fake-IP，也不允许 `10/8`、`172.16/12`、`192.168/16`、回环或链路本地地址。

### 队列时间显示

`GlobalDockQueueOverlay.tsx` 导入并调用现有的 `formatTimeBeijing`。数据库和 API 保持 UTC 契约不变，只修正展示层。

## 测试

- 后端先增加失败测试，证明通用传输仍拒绝 `198.18.0.0/15`，抖音受信任 HTTPS CDN 可接受该网段，非抖音域名、HTTP 和普通私网仍被拒绝。
- 前端先增加组合测试，要求队列浮层调用 `formatTimeBeijing(item.created_at)`，并禁止继续使用 `slice(0, 19)`。
- 运行相关后端单测、前端组合测试、类型检查和构建；随后运行完整后端测试。

## 部署与验证

从最新 `origin/main` 建立隔离分支，避免覆盖当前工作区已有改动。部署前备份生产数据库并记录当前版本；构建新 wheel 后校验哈希、安装到新版本目录并切换 `runtime/current`，保留现有版本用于回滚。

部署后验证服务健康、数据库 `PRAGMA quick_check`、队列 API 时间原值与浏览器北京时间显示。对用户刚提交的失败任务不直接改库；通过现有“重试”操作重新执行，并确认任务越过“下载视频”阶段直至完成。若失败，立即保留现场并回滚应用版本，不删除任务或接入内容。
